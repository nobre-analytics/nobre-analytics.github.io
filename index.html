Three tools from one collections operation, rebuilt so you can use them

I designed and built these screens for the daily work of a credit recovery operation in Brazil. The real versions run on internal data, so these copies use made-up cases and open in your browser with no login.

My role
Process design, business rules and front end
Data
Fictitious. No name, CPF, contract or amount is real
Runs on
Desktop and mobile, light and dark theme

How the three tools connect

Each morning, bots collect data from the operation's systems. The tools below take it from there, in this order.

  1. Step 1Bots collect the data

    Collections system, payment gateway, creditor files and email tasks.

  2. Step 2The Brain checks the morning

    Did every bot run? How much came in? What failed?

    See the tool
  3. Step 3Rejections routes each payment

    A rule engine sends every rejected payment to the queue for its fix.

    See the tool
  4. Step 4FIDC panel refunds duplicates

    Payments made twice are matched with the bank statement and refunded.

    See the tool

Monitoring, on desktop and mobile

The Brain

A monitor for the fleet of data bots. It answers in seconds whether the morning closed, how much came in and what failed.

Problem
The operation depends on bots that run before the workday, and a failed run has to be spotted before people start working.
Built
One screen with every bot, task and source, each with the time its data was saved. A mobile redesign puts the verdict first.
Try
  • Open the failed task to see the step where it stopped
  • Press Ctrl K to jump between sections
  • On mobile, tap the notes beside the phone

Rejections, dashboard

Business rules for payment handling

Payment rejections

Every rejected payment arrives already diagnosed and lands in a queue named after the action it needs.

Problem
The destination of each payment depended on who was on duty, and every case became a ticket.
Built
Written rules with a recorded reason for every decision, queues by action, a write-off bot and a dashboard of the payment path.
Try
  • Open the Issue queue and run the write-off bot
  • Use Grind mode: J next, K back, X done
  • Open the details of a case to see the engine rule

FIDC refunds, operation mode

Reconciliation and refunds

FIDC refunds

Duplicate payments matched against the gateway statement: the original stays, the duplicate is refunded.

Problem
Customers who paid twice need a refund, but each duplicate has to be confirmed against the bank statement first.
Built
Two modes on one screen: curation for who decides what goes into the batch, operation for who requests and completes each refund.
Try
  • Switch to curation mode and change a case to Review
  • Send a case back to the rejections panel
  • Mark a refund as requested, then complete it

Brazilian terms on these screens

The operation runs in Brazil, so a few local terms appear in the tools.

Boleto
A bank payment slip, one of the most common ways to pay bills in Brazil.
Pix
Brazil's instant payment system, run by the Central Bank.
CPF
The individual taxpayer ID. Always masked on these screens.
FIDC
A receivables investment fund that buys credit portfolios.
