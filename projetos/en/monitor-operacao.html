Operations monitoring

How I made failures in the pre-workday routines visible

I brought the status of the operation’s automated routines onto one screen: whether the morning closed, what failed and at which step it stopped. The same information now has a version for the manager’s phone.

The problem

An overnight failure needs to show up before the team starts.

The operation depends on routines that collect and prepare data before the workday. If one fails and nobody notices, the team works all day with incomplete information.

The problem was not only running the routines. It was knowing, quickly, whether the morning was ready and, if not, where it had failed.

Not every registered routine runs on a schedule: some are started when needed and others are switched off. The monitor had to show the real status of each one instead of presenting everything as working.

My contribution

I designed the screen, the retries and the fix for a data bug.

What I did myself
  • Organised the screen around three questions managers ask: did the morning close, how much came in and what failed.
  • Set up the status checks, the retries and the automatic restart with a limit.
  • Investigated and fixed the cause of values that sometimes appeared wrong.
  • Wrote the operator manual.
  • Redesigned the screen for mobile.
External dependencies
  • The routines and the source systems for the data.
  • The final morning check stays with the person responsible.

How it works

The verdict on one screen, the detail one click away.

  1. Collection. Each routine writes its data and the time of the last write. automated
  2. Check. The monitor checks each routine’s status and the step where a failure stopped. automated
  3. Retry. A failed routine runs again, up to a set number of attempts. automated
  4. Handoff. If the retry does not fix it, the case goes to a person. person
  5. Verdict. The first thing on the screen answers whether the morning closed. automated and person

When a source does not respond, the screen shows “no data” instead of zero. A false zero looks like a bad day; “no data” shows that something needs checking.

The bug that made values appear wrongSymptom, cause and fix

Symptom: payment values and sequence numbers sometimes appeared wrong. Once a number is wrong, nobody trusts the panel again.

Cause: two updates wrote the same data with no guaranteed order, and the screen sometimes read a file that was only half written. The technical name for this is a race condition.

Fix: I changed the write so the data is saved in one go, with a lock, so a read always finds a complete version.

What changed

Failures are visible on one screen, with the step where they stopped.

The manager can see whether the morning closed without opening each system, and the team sees the step where a task stopped. After the automatic retries, it is clear when a person needs to act.

How the result was assessedQualitative result

The result is qualitative. Time saved compared with checking by hand has not been measured. The demo’s states are simulated and do not prove real executions.

Mobile extension

On a phone, the question becomes “do I need to act now?”.

The mobile version is an extension of this monitor, not a separate project. The morning verdict comes first, and the detail is one tap away. The expected benefit, the manager knowing in a few seconds whether to act, has not been measured yet.

Limits

What the monitor does not guarantee.

  • It does not replace the check by the person responsible. human step
  • It does not turn routines that are started by hand or switched off into scheduled ones.
  • Email alerts are not active in the latest configuration.
  • How much earlier failures are now noticed has not been measured.

Technical details

Automation with monitoring built in.

Tools, terms and implementation decisionsFor readers who want the detail

Restart with a limit: a failed routine is restarted automatically a few times. The limit is there so a recurring problem is not hidden: after it, the case goes to a person.

Atomic write: the data is written in full in one step, so a reader never finds a half-written file.
